# 運用

この文書はサービス稼働中のデータ、障害時の動作、バックアップと復旧を扱います。インストールと Caddy 設定は [セットアップ](setup.md)、障害の切り分けは [トラブルシューティング](troubleshooting.md) を参照してください。

## データベースの役割

OAuth モードでは、用途と寿命の異なる3つの SQLite ファイルを別々に管理します。

| 設定キー | 内容 | 削除・紛失した場合 |
|---|---|---|
| `database.path` | 既存 OCR データベース。通常の Repository は読み取り専用で接続。書き込みが有効なときだけ同じファイルへ別の書き込み接続を開く | OCR データと専用編集履歴が利用できなくなる |
| `oauth.databasePath` | OAuth クライアント、認可コード、OAuth トークン | クライアントの再認可などが必要になる |
| `staticTokens.databasePath` | 名前付き静的トークンのハッシュ。OAuth のログイン用トークンもここに保存 | 発行済み静的トークンが無効になる |

これらのファイルは別々のパスにしてください。認証データベースの作成時は DB ファイルを `0600`、親ディレクトリを `0700` とする設計です。サービス実行ユーザーに必要なアクセス権を与え、他のユーザーから不用意に参照・変更できないようにしてください。

OCR データベースは別プロジェクトと共有されています。MCP 側で既存の OCR スキーマや `ocr_log` を勝手に変更しないでください。バックアップ手順は OCR DB を管理するアプリの運用と調整します。

## バックアップ

- OCR DB、OAuth DB、静的トークン DB を別々のデータとして扱い、必要な復旧対象を明確にします。
- 認証 DB のバックアップには、元のファイルと同等のアクセス制限を適用します。
- 稼働中の SQLite ファイルを単純にコピーする運用に依存せず、整合性のあるバックアップ方法を選びます。確実性を優先する場合はサービスを停止してからバックアップし、復旧後にアクセス権も確認します。
- OCR DB のバックアップは、同じ DB を利用する既存 OCR アプリ側の更新と整合する方法で行います。
- トークン DB を失うと、そこに保存されていたトークンは復旧できません。安全なバックアップがない場合は新しいトークンを発行し、クライアント側も更新します。

## 起動時の障害と劣化運転

方針は「設定の構造ミスは起動を止める。環境の問題ではサーバーを止めず、該当機能を劣化させる。ただし認証の障害では MCP を閉じる」です。

| 状況 | 起動・リクエスト時の動作 | 復旧方法 |
|---|---|---|
| 設定の構造ミス（相対パス、DBパスの重複、必須設定の欠落など） | 起動しない（終了コード 1） | 設定を修正して再起動 |
| OCR DB を開けない、FTS5やスキーマの検証に失敗 | 起動する。OCR ツールは MCP のエラー結果 (`isError: true`) を返す | 原因を直して再起動 |
| OAuth DB または静的トークン DB を開けない | 起動する。`/mcp` と DB を要する OAuth 操作は 503。メタデータは提供 | 原因を直して再起動 |
| 元画像ストレージを使えない | 起動する。画像ツールが固定のエラー結果を返す | パスをリクエストごとに解決するため、マウント後のリクエストから再試行可能 |
| OCR 書き込み用 DB 接続・履歴初期化に失敗 | 起動する。読み取り機能は継続し、`update_ocr_text` は `write_unavailable` を返す。詳細は標準出力へ記録 | 原因を直して再起動 |

`ocrWrite.enabled` はデフォルト `false` です。`true` にする場合は `auth.mode: "oauth"` が必須です。書き込み用接続が起動時に利用できなければ、読み取り機能を維持して書き込みだけを無効扱いにします。

起動時に開けなかった DB を自動で開き直す仕組みはありません。原因を修正した後は再起動してください。認証 DB が利用できない場合に、認証なしで MCP を公開することはありません（fail-closed）。

通常の OCR DB・ストレージ障害は、HTTP 503 によって接続全体を閉じるのではなく MCP のツール結果で報告します。認証機構が使えない場合は `/mcp` を 503 にします。


## OCR 書き込みの制限

- `update_ocr_text` は `source_images.ocr_text` の全文置換です。`reviewed != 0` の行は、本文が同じ場合も拒否します。
- 本文は 20,000 UTF-16 コード単位かつ UTF-8 で 64 KiB 以下です。既存本文がその上限を超える行も、部分テキストで上書きしないよう拒否します。
- 本文更新と `mcp_ocr_edit_history` への旧本文・新本文・UTC時刻の記録を同一トランザクションで行います。履歴の書き込みに失敗すれば更新もロールバックします。同じ本文は `changed: false` を返し、履歴を増やしません。
- 書き込み用 SQLite 接続の busy timeout は 500 ms です。直近60秒でクライアント単位10回、サーバー全体30回を超える書き込み要求は拒否されます。
- MCP サーバーは HTTP リクエスト本文を 1 MiB に制限します。Caddy の設定だけに依存せず Node.js 側でも実測バイト数を検査します。
- 履歴の `old_text + new_text` の UTF-8 バイト数推定が 10 MiB に達すると、標準出力へ一度警告します。これは SQLite ファイル全体のサイズではありません。履歴は自動削除しません。
- 履歴推定値は起動時に集計し、その後はこの Node.js プロセス内で成功した書き込み分を加算します。レート制限もプロセス単位です。同じ OCR DB を複数の MCP サーバープロセスから同時に書く運用は想定していません。
- `source_images` の既存 FTS5 更新トリガーを利用します。MCP から FTS テーブルを直接変更したり、全件 reindex を実行したりしません。

## ログと秘密情報

- 起動・運用ログには障害の詳細やローカルパスが含まれることがあります。ログファイルとログ閲覧権限を管理してください。
- トークン本体、認可コードの生値は DB に保存せず、ハッシュを保存します。ログには秘密のトークン本体を出さない設計です。
- systemd などで常駐させる場合は専用の非特権ユーザーを使い、DB と画像ファイルに必要な最小限のアクセス権を与えます。

## 停止と再起動

`npm start` で起動したプロセスを停止する際は通常のプロセス終了シグナルを使います。アプリケーションは保持している DB リソースを閉じる処理を持っています。設定・パス・DBの状態を変えた後は、変更が反映されるように再起動してください。

OAuth DB だけを消すと OAuth クライアントやトークンの状態が失われます。静的トークン DB は別ファイルなので、別の影響があります。不要な DB 削除を復旧手段として安易に使わず、まず [トラブルシューティング](troubleshooting.md) で症状を確認してください。
